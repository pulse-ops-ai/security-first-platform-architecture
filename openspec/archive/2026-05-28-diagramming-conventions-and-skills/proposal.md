# OpenSpec Proposal: Diagramming conventions + drawio / mermaid skills

## Problem

Two consumers are now adopting the architecture (trupryce, platform-edge). Both have already produced — or will need to produce — diagrams that depict trust zones, layer interactions, deviations, and deployment topology. Today there is **no shared visual vocabulary**, no canonical tooling guidance, and no skill that an agent can invoke to produce a diagram against the workspace's conventions.

Concrete evidence:

- trupryce's `security-first-adoption.md` records four deviations including DEV-002 (shared-secret service-trust vs ADR-0003 Z4 envelope). The deviation is described in prose but has no visual representation; an auditor reviewing the adoption record cannot quickly see where in the trust-zone model the deviation sits.
- The platform-edge orientation report flagged that the brief's "L5→L6 envelope seam" framing conflicts with the actual L6→L7 seam per ADR-0003. This kind of seam mis-placement is hard to catch in prose and trivial to catch with a layered diagram.
- Every future onboarding will run into the same need: "explain how my deployment maps to L1–L8," "draw my deviations," "show my agent-as-client path." Without conventions, every consumer invents its own visual language, and cross-repo audits become harder, not easier.

Independently, the workspace already has the `mcp__claude_ai_draw_io__create_diagram` MCP tool available, and the `drawio` desktop CLI ships on most developer machines. The plumbing exists; what is missing is the **architectural pairing** — a standard that says *what* a workspace diagram should look like, and a skill that knows *how* to produce one.

## Proposed change

Two coordinated additions, in one PR.

### 1. `standards/diagramming-conventions.md` (new)

A vendor-neutral standard defining the workspace's visual vocabulary:

- **Trust-zone colours (Z0 → Z4)** — fixed background fills for `Z0` (untrusted, light red) through `Z4` (envelope-protected, light purple). Not negotiable per consumer.
- **Layer ribbons (L1 → L8)** — horizontal stripes with fixed stroke colours per layer, showing services within each ribbon.
- **Agent-as-client lane** — a dashed grey lane (visually enforcing ADR-0002) showing agents traversing L1/L2 like any human user; never a back-channel into L7.
- **Deviation marker** — red dashed border + `DEV-NNN` callout matching the consumer's `security-first-adoption.md` `deviations:` list.
- **Envelope crossing (Z3 → Z4)** — signed-arrow glyph for L6→L7 trust transitions (the most security-critical seam).
- **File-location convention** — `architecture/diagrams/` in the architecture repo, `docs/diagrams/` in consumer repos. Each with an `INDEX.md` carrying `last_reviewed:` / `next_review:` per entry.
- **Source-of-truth citation in every diagram footer** — required convention to mitigate drift.
- **Drift mitigation** — quarterly review cadence in INDEX, source-of-truth citation, optional future CI validator.

### 2. Two new skills under `.agents/skills/`

- **`drawio/`** — authors and exports `.drawio` files. Handles WSL2, macOS, native Linux, ARM64 headless, and the drawio MCP fallback. Includes two reference files (`edge-routing.md` for layout problems, `x86_64-install.md` for install/headless setup). The skill applies the conventions standard when the diagram is architectural.
- **`mermaid-diagram/`** — authors Mermaid sequence / flowchart / state / ER / class diagrams as fenced ```` ```mermaid ```` blocks inline in markdown (renders natively in GitHub). Companion to drawio for diagrams that should not live in a separate file. Includes one reference file (`architecture-vocab.md`) mapping the conventions standard to Mermaid patterns (zone notation in participant labels, agent-as-client styling, envelope-crossing annotations, deviation callouts).

Both skills get vendor adapter shims (`.claude/skills/`, `.codex/skills/`) and Claude slash commands (`.claude/commands/drawio.md`, `.claude/commands/mermaid-diagram.md`) generated by `sync-agent-skills.sh --bootstrap`.

### Format choice (drawio vs Mermaid)

Per the new standard §Format choice:

- **Drawio** for layered architecture, trust-zone overlays, deployment topology, dependency graphs. Multi-layer spatial work needs proper boxes, lanes, and corridor routing; Mermaid does not handle this well.
- **Mermaid** for request sequences, OAuth/OIDC flows, agent-as-client routing, incident timelines. Renders natively in GitHub markdown; no second source-of-truth file to keep in sync.

The skills are **complementary, not redundant**. Each format does what the other cannot.

### Deliberately deferred (Phase 2, future PR)

- **Example diagrams** under `architecture/diagrams/`. The user's choice was Option 3 (skill + standard + examples), but authoring complex drawio XML by hand without being able to render it for visual validation would compromise the "professional" goal. Phase 2 will produce the example diagrams *using the skill we are shipping*, which dog-foods the foundation and ships visually-validated PNG/SVG renderings alongside each `.drawio` source. Scope of Phase 2: one canonical eight-layer-control-model diagram + one self-hosted-vps deployment-topology diagram (the profile both current consumers use).
- **`validate-diagrams.sh` CI hook**. Flags `.drawio` files whose footer `Last reviewed:` is more than 90 days old when the diagram or its cited doc changes. Useful for drift mitigation but not load-bearing for the first release.

## Alternatives considered

- **Skill only, no standard.** A single `.agents/skills/drawio/` skill, no conventions doc. Smaller PR, lower OpenSpec ceremony. Rejected because each consumer would invent its own visual vocabulary — trupryce already has four deviations; without conventions, each consumer's deviation diagrams would look different from every other consumer's. Cross-repo audits would get harder, defeating the point of the shared architecture repo.
- **Standard + one skill (drawio only), defer Mermaid.** Sequence diagrams could be authored by hand. Rejected because the most common diagrams consumers will produce *are* sequence diagrams (request flows, OAuth journeys, agent routing). Forcing those into drawio is the wrong tool; forcing consumers to author Mermaid by hand without architectural vocab guidance is the wrong choice. Both tools, both with vocab references, both shipped together.
- **Standard + skills + reference diagrams in the architecture repo.** The user's preferred Option 3. The skill + standard ship now; the reference diagrams are deferred to Phase 2 (see "Deliberately deferred" above) so they can themselves be produced using the new skill — a dog-fooding validation.
- **Excalidraw as a third format.** Excalidraw has a hand-drawn aesthetic that's popular for whiteboarding. Rejected for v1 because the workspace already has two formats with clear roles and Excalidraw would dilute the "drawio for spatial / Mermaid for inline" rule. A future addition is fine if there's demand.

## Impact

- **Repos affected:** the architecture repo only in this PR. Phase 2 will add `architecture/diagrams/` content.
- **Layers / profiles affected:** none directly. The standard documents how to *depict* layers and profiles, not the layers/profiles themselves.
- **Standards affected:** new file `standards/diagramming-conventions.md`. No existing standard changed.
- **Templates affected:** none in this PR. The consuming-repo template could be extended later to suggest a `docs/diagrams/` folder with a stub `INDEX.md`; left as a follow-up to avoid bloating this PR.
- **Cross-repo contracts:** none. This change is purely additive. No consumer is forced to adopt the skills or the conventions. Consumers that choose to produce diagrams should follow the standard; consumers that do not are unaffected.
- **Security-boundary impact:** none. Diagrams illustrate; they do not enforce. The standard's anti-patterns section explicitly notes "diagrams are not the only place a fact lives — the doc is authoritative."
