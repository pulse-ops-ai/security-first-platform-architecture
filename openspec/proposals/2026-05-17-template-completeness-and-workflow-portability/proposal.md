# OpenSpec Proposal: Template completeness + workflow portability

## Problem

PR #12's first-consumer-onboarding runbook revealed that the `templates/consuming-repo/` tree is **not complete enough to onboard a real consumer** without authoring substantial CI infrastructure by hand. Specifically:

- The template ships no `.github/workflows/` — adopters must hand-copy or hand-author the healthcheck workflows from the architecture repo.
- The template ships no `.claude/` directory — Claude-using adopters get `CLAUDE.md` from the template but no `.claude/skills/`, `.claude/commands/`, `.claude/agents/` shim directories. The repo contract requires `CLAUDE.md` + `.claude/` together when Claude is used; the template only ships half.
- The template ships no `.pre-commit-config.yaml` — adopters either copy the architecture repo's (which references architecture-specific scripts they don't have) or write their own from scratch.
- The template ships no `.gitleaks.toml`, no `.secrets.baseline`, no `CODEOWNERS` template.

Independently, the architecture repo's `.github/workflows/*.yml` are **not consumer-portable** as written. `validate-doc-indexes.sh` and `validate-skills.sh` hardcode their own repo root via `$(dirname $0)/..`, so even if a consumer copied the workflow they couldn't easily run it against their own tree.

Combined, the gaps mean trupryce (the planned first adopter) would hit ~6 hand-build steps in the onboarding runbook that aren't authentic to their team's decisions — they're just busywork imposed by template incompleteness. Fixing this before trupryce onboards keeps the first-adopter experience clean.

## Proposed change

Two coordinated edits, in one PR.

### 1. Make architecture-repo healthcheck workflows reusable (`workflow_call:`)

- `.github/workflows/docs-healthcheck.yml` — adds `workflow_call:` trigger with optional `architecture_ref` input. When invoked from a consumer, the workflow does a dual checkout (caller for content + architecture repo for scripts) and runs `validate-doc-indexes.sh` against the caller's tree.
- `.github/workflows/pre-commit.yml` — adds `workflow_call:` trigger (no inputs needed; pre-commit operates on the calling repo's files generically).
- **NEW** `.github/workflows/repo-healthcheck.yml` — runs `scripts/repo-healthcheck.sh` against the calling repo. Self-mode for the architecture repo's own CI; consumer-mode via `workflow_call:` with `architecture_ref` input.
- `scripts/validate-doc-indexes.sh` — refactored to accept an optional target-path argument (`bash validate-doc-indexes.sh <path>`), defaulting to the script's own repo root when not supplied. Required for the reusable workflow to run the script against the caller's tree.

`skills-healthcheck.yml`, `architecture-healthcheck.yml`, `codeowners-check.yml`, and `openspec-triage.yml` are NOT made reusable in this PR — they're either architecture-repo-specific (architecture-healthcheck), or they'd need parameterization that expands scope (codeowners-check enforces architecture-repo paths). Deferred.

### 2. Complete the consumer template

Add to `templates/consuming-repo/`:

- `.github/workflows/repo-healthcheck.yml`, `docs-healthcheck.yml`, `pre-commit.yml` — thin callers for the reusable workflows above. Each uses `__ARCHITECTURE_REF__` as a placeholder the adopter substitutes during onboarding.
- `.github/CODEOWNERS` — placeholder ownership map with `@<solution-team>` / `@<consumer-lead>` substitution markers.
- `.pre-commit-config.yaml` — consumer-portable subset of the architecture repo's hooks (file hygiene + secrets + shellcheck; no architecture-repo script references).
- `.secrets.baseline` — empty starting baseline generated by detect-secrets.
- `.gitleaks.toml` — narrow allowlist for `.secrets.baseline` (same shape as the architecture repo's).
- `.claude/skills/README.md`, `.claude/commands/README.md`, `.claude/agents/README.md` — adapter-shim directory READMEs.

Plus runbook + contract updates:

- `docs/operations/first-consumer-onboarding.md` — step 2 simplified (template now has everything); step 3 adds the `__ARCHITECTURE_REF__` substitution; step 9 reframed as a confirmation step instead of a configuration step.
- `standards/repo-contract.md` — new "What the consumer template ships" section listing exactly what's in the template so adopters know what to expect before copying.

Plus archive cleanup:

- Move `openspec/proposals/2026-05-17-repo-healthcheck-alignment/` (PR #13's proposal, merged) to `openspec/archive/`. Standard `PR-N+1 archives PR-N` pattern.

## Alternatives considered

- **Bundle scripts into the consumer template instead of using reusable workflows.** Consumer would have a local copy of `validate-doc-indexes.sh`, `repo-healthcheck.sh`, etc. Pros: no architecture-repo CI dependency; consumer's CI is self-contained. Cons: scripts in two places need to stay in sync (drift); consumer has to bump scripts AND the adoption record on every architecture-repo ref change instead of just the workflow `@ref` lines. Rejected because the reusable-workflow path makes ref bumps a one-place edit (in CI yaml) plus a one-place edit (in adoption record) instead of N-place edits across each script.
- **Pin reusable workflows to `@main` in the template, recommend adopters change to a tag.** Simpler template; one fewer substitution. Rejected because `@main` couples the consumer to whatever the architecture repo happens to ship — defeats the whole point of `architecture_ref` pinning. The substitution friction is small (one `sed` command in onboarding) and the resulting clarity is large.
- **Refactor all six workflows (not just three) to be reusable in this PR.** Would address `skills-healthcheck`, `architecture-healthcheck`, `codeowners-check`, `openspec-triage` too. Rejected because (a) `architecture-healthcheck` is architecture-repo-specific by definition; (b) `codeowners-check`'s required-path enforcement needs parameterization to be reusable, which is its own design conversation; (c) consumers may not adopt OpenSpec immediately, so the openspec-triage reusable can wait. Doing the three highest-value ones now and deferring the rest keeps this PR focused.
- **Skip the consumer pre-commit / gitleaks / secrets baseline templates; let adopters bring their own.** Lighter scope. Rejected because trupryce explicitly will copy these from the architecture repo if they're not in the template, and the architecture repo's versions reference scripts trupryce doesn't have. Either we ship consumer-portable versions in the template, or the first-adopter experience involves "copy this, then strip out the hooks that don't work."
- **Add the `.github/workflows/` to `templates/consuming-repo/` but keep workflows as standalone scripts (not reusable).** Smaller architecture-repo change. Rejected because consumer's workflow would then need to vendor each script (and bump them on every ref change). The reusable-workflow design centralizes that update in one architectural place.

## Impact

- **Repos affected:** the architecture repo only in this PR. The trupryce onboarding PR (next, in trupryce's repo) will be the first user.
- **Layers / profiles affected:** none.
- **Standards affected:** `standards/repo-contract.md` gains a new "What the consumer template ships" section (no contract change). `standards/ci-cd-standard.md` updated to reconcile the §Required workflows table with the post-PR-9 reality: `repo-healthcheck.yml` is now the universal floor (was `architecture-healthcheck.yml`, which is architecture-repo-specific); `pre-commit.yml` added to floor; `skills-healthcheck.yml` made conditional.
- **Templates affected:** `templates/consuming-repo/` substantially expanded.
- **Cross-repo contracts:** introduces the **reusable-workflow contract** between architecture repo and consumers. A consumer's `.github/workflows/repo-healthcheck.yml` carries a `uses: …@<ref>` line that pins to a specific architecture-repo ref; that ref must match the consumer's `security-first-adoption.md` `architecture_ref:`. This is documented in the new repo-contract section and in the runbook step 3.
- **Security-boundary impact:** none directly. The reusable workflows run the same scripts they would have run otherwise; only the invocation path changes.

## Note on tier classification (script vs intent)

`scripts/openspec-triage.sh` classifies this PR as **Tier 3** because the diff touches `standards/repo-contract.md`, which is in the script's Tier-3 path list. The script is path-based; it cannot distinguish a substantive contract change from an additive documentation section.

The actual diff in `repo-contract.md` is a new "What the consumer template ships" section that *describes* what we're adding to the template. No rule in the Universal Floor or Vendor-Specific Adapter contract changes — the eight-layer model, agent-as-client rule, internal envelope, multi-tenancy, and security-boundary contracts are all untouched.

This proposal therefore declares `tier: 2` to match the *intent* of the change. The triage script PASSes (it doesn't BLOCK on tier-mismatch between diff and proposal), so CI is unblocked. The same over-classification pattern was acknowledged in PR-7 for `architecture/agent-as-client-model.md` and `architecture/internal-identity-envelope.md` callout additions. Tightening `is_tier3_file` to recognize additive-doc-only diffs remains a known limitation queued for a future PR.
